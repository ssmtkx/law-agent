## 先读这一节：与通用 RAG 的四个差异

如果不先理解这四点，读代码时会觉得很多设计"多余"——**它们全都是实测逼出来的**。

### 1. 一条法条 = 一个 chunk

中国法规天然以「第X条」为语义单元，边界明确，**不需要切分，只需要识别**。

条首必须**行首锚定**（`(?m)^第[一二三…]+条`）。不锚定的话，正文里的引用
（"依照本法第三百零二条规定"）也会被当成条首 —— 实测海商法宽松匹配 382 处
vs 锚定后 310 条。

这条严格性后来还救了兜底切分：那 365 部老式文件里出现的「第X条」**全部是对
其他法规的引用**，正因为锚定严格才没被误当成本文条文。

### 2. 每个 chunk 必须带上下文头

```
《中华人民共和国民法典》（2020-05-28公布，2021-01-01施行）第五百八十五条
当事人可以约定一方违约时应当根据违约情况向对方支付一定数额的违约金……
```

法条大量以「本法所称……」「前款规定的……」开头，脱离法名与条号无法理解。

### 3. 评测真值按 (法名, 条号) 匹配

不用"第 N 段文本"这种位置下标。这一条决定了评测集能否来自语料之外 —— 见第 8 步。

### 4. **查询改写是链路的第一步，精排默认关闭**

用户口语（"公司拖欠我三个月工资我能主张什么"）与法条书面语存在语域差，向量
对不上。所以先用 LLM 把问题改写成法条语域再检索。

而 CrossEncoder 精排**默认关闭**：它用**用户原问题**打分，而那正是因语域差而
失效的信号，实测会把改写的收益整个抹平（0.567 → 0.233）。详见第 5 步。

## 推荐阅读顺序（自底向上，11 步）

### 第 1 步：领域常量 — `src/domain.py`（57 行）

先读这个。助手身份、知识库范围、集合名、免责声明全在这里。

**为什么单独一个文件**：上一版把同一句「四项分类」硬编码在 6 个文件里，
persona 提示词有两份互不引用的副本，换域时要靠人肉搜索，而漏改是**静默的**
（UI 卡片显示错内容、集合名对不上）。领域相关的字符串现在只有一个来源。

---

### 第 2 步：数据摄入层 `src/ingestion/` — 条文怎么进来的

| 文件 | 行数 | 核心逻辑 |
|------|------|----------|
| `law_parser.py` | 467 | ⭐ **法规解析**：docx/PDF → 段落 → 条文 → 带上下文头的 chunk |
| `splitter.py` | 116 | 通用中文分块（非法规文档用） |
| `parser.py` | 50 | 通用 PDF 解析：PyMuPDF（主）+ pdfplumber（兜底） |

`law_parser.py` 有两类：

- `LawTextParser` — `parse_docx`（zipfile 直读 XML，不需要 python-docx）
  → `parse_pdf`（扫描件兜底）→ `extract_articles`（识别条首、追踪编/章/节）
  → `_extract_fallback`（三级兜底）
- `LawArticleSplitter` — 注入上下文头，生成带 metadata 的 chunk

**三级兜底切分**值得细看。语料里约 18% 的文件不用「第X条」编号：早期规范性
文件与修改/补充决定用「一、」或「（一）」，批复/复函是无编号散文。

| 级别 | 依据 | 防误判设计 |
|---|---|---|
| 1 | `一、` 行首 | 要求 ≥2 个标记，否则散文里偶然一个「一、」会凭空造出层级 |
| 2 | `（一）` 行首 | 同上 |
| 3 | 段落分组 | 跳过版头（判定用"段落过短 **或** 含版头提示词"） |

第三级的判定条件是有讲究的：只看长度会漏掉「…已于…会议通过，现予公布」这种
**既长又是版头**的段落。

**易错点**：条号必须先拆「之N」再转数字。直接整串转中文数字会把结尾的「一」
算进去，`第十七条之一` 得 11 而不是 17 —— 这个 bug 在 `law_parser.py` 和
`evaluator.py` 里各犯过一次，所以抽成了 `src/utils/cn_numeral.py` 共享。

### 第 3 步：语料采集 `scripts/crawl_laws.py`（570 行）

项目最长的文件，解决的是"从一个有反爬的政府站点稳定取数"。

| 机制 | 位置 | 说明 |
|------|------|------|
| 枚举 | `search_page` | 按**叶节点**分类码分页；父节点码会返回 total=0 |
| 下载 | `fetch_document` | 详情接口的 `content` **实测恒为空**，正文只能走 docx 下载接口拿签名 URL |
| 解析回落 | `fetch_articles` | docx 不是 zip → 回落 PDF；PDF 无文字层（扫描件）→ 记为**失败**而非"无条文" |
| WAF 处理 | `_request` / `WafGuard` | 轻量时 302+cookie，量大时升级为 **JS 挑战页** |
| 熔断 | `WafGuard.penalize` | 连续 3 次挑战且中间无成功 → 干净退出，而不是空烧几小时 |
| 心跳 | `_heartbeat` | 写 `crawl_heartbeat.json`，让外部能区分「冷却中」和「已死」 |
| 续传 | 主循环 | 只有"已落盘**且切出了内容**"才算完成 —— 这样解析能力升级后重跑即可回填 |

**两个踩过的坑**：

1. 判断"是否被 WAF 拦住"不能只看状态码 —— JS 挑战页也是 `200 + text/html`，
   必须检查响应体是不是 JSON，否则会把"被反爬"误报成"数据格式错误"
2. 熔断异常继承自 `RuntimeError`，一度被单条失败的 `except Exception` 吞掉，
   导致熔断只是把后续每一部标成失败然后继续跑（一次积压了 117 条假失败）。
   每层都要显式 `except SiteThrottled: raise`

配套的 `scripts/crawl_status.py`（267 行）读磁盘状态 + 心跳，输出进度条、
速度、ETA 和失败原因分类。

### 第 4 步：索引构建层 `src/indexing/` — 索引怎么建

| 文件 | 行数 | 核心逻辑 |
|------|------|----------|
| `vector_store.py` | 102 | Chroma 封装 + **分页取数** `fetch_all` |
| `bm25_index.py` | 235 | ⭐ **自实现 BM25**：jieba 分词、IDF 预计算、TF 饱和（k1=1.5, b=0.75） |
| `indexer.py` | 211 | 法规 JSON → 条文 chunk → Chroma；再从整个集合建 BM25 |

三个关键实现选择：

**① `fetch_all` 是必需的，不是优化**

`collection.get()` 不带 limit 时试图一次取回全部记录，Chroma 的 SQLite 后端
因此撞上 `SQLITE_MAX_VARIABLE_NUMBER`（约 32,766）。**实测 27,672 条能通过，
54,618 条报 "too many SQL variables"** —— 这个 bug 只在规模上去之后才出现。

**② 词频用 `Counter` 而非词表**

`search()` 只需查词频。用 `List[str]` 会导致每命中一个 posting 就线性扫一遍
文档；8 万块规模下这既是速度问题也是 pickle 体积问题。

**③ 缓存指纹必须含 schema 版本**

`_doc_signature` 只哈希文档文本时，代码新增 `_doc_ids`/`_doc_metas` 字段后
**旧缓存仍被判为"新鲜"**，被静默加载 → id 退化成 `chunk_{i}`、与向量库真实 id
对不上 → 融合去重失效（同一块在 top-5 出现两次）+ 元数据全丢（引用退化成
「知识库」）。`load()` 现在遇到版本不匹配直接返回 `False` 让调用方重建。

`indexer.py` 还做**同版本去重**：源库里存在同标题、同效力状态、条文完全相同
但 `bbbs` 不同的条目（实测公司法、村民委员会组织法各有两份），不去重会产生
重复块互相竞争排名。

### 第 5 步：检索层 `src/retrieval/` — 引擎核心 ⭐

| 文件 | 行数 | 核心逻辑 |
|------|------|----------|
| `query_expander.py` | 228 | ⭐ **HyDE 查询改写**（默认启用） |
| `hybrid_retriever.py` | 237 | BM25 + 语义 → **RRF 融合** + 相关性下限 |
| `reranker.py` | 173 | CrossEncoder 精排（**默认关闭**，用于对比实验） |
| `factory.py` | 89 | 检索链组装，决定默认接入哪些层 |

#### `query_expander.py` 是理解这个项目的关键

用户口语与法条书面语存在语域差。做法是让 LLM 生成一段"如果法律要回答这个
问题，条文大概会怎么写"的文字，**拼在原始问题后面**一起嵌入。

保留原问题的原因是它承载了提问者的事实描述（时间、金额、当事人），那部分信息
生成的法条里没有。

**实测**（148 条评测题，同一批题）：

| 查询表示 | @20 | @50 | @100 |
|---|---|---|---|
| 原始问题 | 0.480 | 0.649 | 0.723 |
| **问题 + 假设性条文** | **0.757** | 0.872 | 0.905 |

三个工程细节：

- **`reasoning_effort="none"`**：改写是**机械转换**，不需要法律分析。不设限时
  模型推理长达 7000 字，既慢又会把预算耗光导致正文为空；关掉之后质量不变而
  快 10–27 倍（25 秒 → 3.5 秒），空结果率从 6–9% 降到 0
- **提示词要"机械"**：用「你是一位立法工作者…」这类身份设定会诱发大量推理
- **累计预算闸**：超过总预算后整层自行关闭、余下查询直接透传。没有这道闸时，
  API 变慢会让每条查询都等满超时（实测一次评测因此静默卡了 56 分钟）

#### `hybrid_retriever.py` 的融合选择

用 **RRF**（Cormack SIGIR 2009，只用名次）而非分数归一化：

    score(d) = α/(k + rank_bm25(d)) + (1-α)/(k + rank_dense(d))

分数归一化的问题在于两路分数本就不可比（余弦在 [-1,1]、BM25 无上界），而组内
min-max 还让结果依赖**当前查询候选池的极值**。更糟的是它没有下限：池子里全是
无关条文时，"最不无关"的那条照样归一化到 1.0。

**但实测两者召回无差异**（@20 0.547 vs 0.554，@100 0.736 vs 0.723）。选 RRF
是因为不需要分数校准、代码更短，**不是因为它更快或更准**。

`DEFAULT_MIN_SIMILARITY = 0.0`（关闭）也有注释说明原因 —— 见第 8 步末尾。

#### `reranker.py` 为什么默认关闭

```
无改写 + 无精排   Hit@5 = 0.133
有改写 + 无精排   Hit@5 = 0.567   ← 生产配置
有改写 + 精排     Hit@5 = 0.233   ← 精排把改写的收益吃掉了
```

原因是交叉编码器用 `(用户原问题, 条文)` 打分 —— 而"用户原问题"正是那个因语域差
而失效的信号。

**但"换个信号就对了"这个推论也被实测推翻了。** 把 HyDE 包到精排**外层**（改写
文本同时用于召回与打分），同一批 25 条题：无精排 Hit@5 = **0.520**，有精排 =
**0.280**。另外查过 CrossEncoder 的有效长度是 8192（模型配置 8194，tokenizer
8192，`max_length=None` 时不覆盖），我们的输入约 500–600 token，**不存在截断**。

所以既不是信号问题、也不是长度问题 —— **该精排模型在这条任务上就是不行**。
它同时是最慢的一环（约 10 秒/条），生产配置永久关闭。需要时用
`factory.build_retriever(rerank=True)` 打开做对比实验。

**顺带一个诚实的标注**：既然排序提不上去，当前靠 `top_k=12` 缓解。实测召回率
随 k 持续上升（@5 0.540 → @12 0.667），但 **MRR 从 k=8 起平在 0.44** ——
说明加大 k 是在**绕开**排序问题，不是在解决它。完整的 k 曲线见
[问题与解决方案.md](问题与解决方案.md) 第 36 条。

文件里还留着两个**已修的坑**的注释，读的时候值得留意：
重复 sigmoid（让拒答变死代码）、加权乘在负 logit 上（方向反了）。

### 第 6 步：生成层 `src/generation/` — RAG 问答模式

| 文件 | 行数 | 核心逻辑 |
|------|------|----------|
| `prompts.py` | 75 | Prompt 模板：身份 / 闲聊 / RAG / 拒答 |
| `rag_pipeline.py` | 228 | ⭐ **LawAgent**：意图分拣 + 记忆 + RAG + 拒答 |

**`reasoning_effort="low"` 这个参数值得单独看**：

| 设置 | 耗时 | 推理 | 正文 |
|---|---|---|---|
| 不设 | **78.9s** | 9402字 | 1058字 |
| `low` | **9.4s** | 192字 | **1223字** |

不设限时模型**过度推理** —— 把预算耗在分析上，正文反而更短。而且这正是**空答案
的根因**（推理吃光 `max_tokens`，`content` 一个字都不剩，`finish_reason="length"`）。

`LawAgent` 另外两点：

- `_is_chat()` 关键词匹配分流；`≤4 字` 的残余长度判断让「你好，劳动合同违约金
  怎么算？」不会被误路由到闲聊
- 检索结果为空 → 走拒答，**不调用 LLM**
- `_source_name()` 从 metadata 渲染成 `《法规名》第X条`；元数据缺失会退化成
  「知识库」，所以它是引用质量的可观测信号

### 第 7 步：Agent 层 `src/agent/` — 法律分析模式

| 文件 | 行数 | 核心逻辑 |
|------|------|----------|
| `tools.py` | 246 | 3 个 function-calling 工具 + `ToolExecutor` |
| `react_agent.py` | 353 | ⭐ **LawReActAgent**：ReAct 循环，max 10 轮 |

工具**结构**沿用上一版（一个通用检索 + 两个侧面检索），换的是描述与
**查询增强串**：

| 工具 | 增强串 |
|------|------|
| `query_tool_list` | `f"{technique} 法律规定 条文 适用 依据 相关法规"` |
| `check_common_mistakes` | `f"{step} 常见误区 法律风险 责任 举证 时效 注意事项"` |

增强串不经过 LLM，但直接决定召回质量。换成设备类词汇会把召回拉向完全无关的
条文。

**关于 Agent 路径的改写开销（已测量，结论是不改）**

每个工具调用都会触发一次 HyDE 改写，`max_iterations=10` → 最坏累计 37 秒，且
改写**串行**（必须等它完成才能检索，无法与其他步骤并行）。

曾考虑"只改写用户原问题、工具查询跳过改写"来省这笔开销。**实测否掉了这个方案**
（`scripts/measure_agent_queries.py`，60 条题）：

| 查询形态 | @20 改写前→后 | 增益 |
|---|---|---|
| 完整问题 | 0.47 → 0.80 | **+0.333** |
| 关键词式（法条清单） | 0.42 → 0.50 | +0.083 |
| 关键词式（风险误区） | 0.35 → 0.50 | +0.150 |

工具式查询的增益小得多（语域差在自然语言问题上最大，关键词串本就没多少"口语"
可搬），**但仍然是正的**。跳过改写的代价是 8–15 个点的召回，换 37 秒的**最坏
情况**——不划算。

而且缓存已经在起作用：`query_tool_list("劳动合同解除")` 只要 technique 相同就命中
缓存，重复查询零成本。真实开销比 37 秒的最坏值低得多。

**结论：保持现状。**

### 第 8 步：评测体系 — 本项目最值得看的部分

| 文件 | 行数 | 核心逻辑 |
|------|------|----------|
| `src/eval/evaluator.py` | 504 | 指标 + 覆盖度 + 拒答率 |
| `eval_rag.py` | 269 | 检索评测 CLI |
| `eval_agent.py` | 385 | Agent 回答质量四维评分 CLI |

#### 上一版评测是自证循环

旧实现用 `relevant_chunk_indices`（指向硬编码 Python 列表的下标）作为真值。
后果是评测题**只能照着语料写**：问题成了答案的改写。README 里那个
「知识库内 Hit@5 = 100%」实际是 42/42 —— 与 84%（42/50）是同一个数字的两种
写法，不携带任何信息。

#### 新设计的两条约束

1. **真值按 `(法名, 条号)` 匹配 chunk metadata**，不按文本位置 → 评测集可以
   脱离语料编写
2. **单独报告语料覆盖度**：

```
  语料覆盖度（先看这个，再看指标）
  黄金条文覆盖率: 91.7%
  可答条目: 6337/6914
```

覆盖率低说明**语料不全**，此时 Hit Rate 只是语料完整度的代理指标。

#### 三个容易踩的方法论坑

**① 采样不能按法名分层**。各法规在评测集里的条数相差两个数量级（民法典 1935
vs 公司法 51），各取等量会把小法超采样几十倍。实测这样采出的 72 条样本上
Hit@5 只有 0.125，而全量是 0.319 —— 样本比全集难得多。见 `sample_dataset()`。

**② 指标分母要用实际召回条数**。相关性下限会过滤候选，"返回 0 条"时那些
空槽位根本不存在。用 `样本数 × max_k` 做分母会把"拒答生效"算成"元数据丢失"
（实测虚高到 81.1%）。

**③ 拒答率的分母是"应当拒答"的条目数**，误拒率的分母是其余条目数。

#### 配套的诊断脚本

| 脚本 | 用途 |
|---|---|
| `diagnose_recall.py` | 候选池召回率 @20/@50/@500，分 BM25/语义/融合三路 |
| `test_hyde.py` | 四种查询表示的对比实验 |
| `tune_threshold.py` | 相关性下限的工作曲线（分数算一次，离线扫阈值） |
| `build_eval_set.py` | 从 EQUALS 构建评测集 + 核对覆盖度 |

`diagnose_recall.py` 是定位瓶颈的工具：**它能区分"找不到"（召回问题）与
"排不上"（排序问题）**。正是它测出正确条文在 @500 里有 86%、@20 只有 48%，
从而把方向指向查询改写而非换嵌入模型。

#### 关于拒答的一个未解问题

`hybrid_retriever.DEFAULT_MIN_SIMILARITY` 默认 **0.0（关闭）**，注释里写了原因：

```
库内问题  n=141   0.822 – 0.984
域外问题  n= 12   0.770 – 0.915
                        ↑ 域外最大值高于库内最小值，两条分布重叠
```

**查询改写越有效，"语料能不能答"这个信号就越弱** —— 它把"明天天气怎么样"
也改写成法条腔，于是总能匹配到真条文。拒答目前只靠提示词层约束。

## 项目亮点

1. **真实语料**：从国家法律法规数据库采集，按条文切分，非手工示例
2. **可定位的召回诊断**：`diagnose_recall.py` 能区分"找不到"与"排不上"
3. **查询改写**：把口语问题搬进法条语域，召回 @20 提升 28 个点
4. **反爬工程**：WAF 识别、自适应冷却、熔断保护、心跳可观测、断点续传
5. **可信评测**：真值按 (法名, 条号) 匹配，评测集独立于语料，单独报告覆盖度
6. **装饰器模式检索链**：每层相同 `.query()` 接口，可任意组合替换
7. **104 个测试**，覆盖条文解析、兜底切分、缓存失效、指标计算、UI 一致性

## 附录：这个项目修过的坑

完整版见 **[问题与解决方案.md](问题与解决方案.md)**（37 个问题）。核心的几个：

| 问题 | 症状 | 根因 |
|---|---|---|
| **拒答从未生效** | 问天气也返回国旗法 | `predict()` 已含 sigmoid，又套一层 → 阈值失效 |
| **问答返回空答案** | 一个字都没有 | 推理模型吃光 `max_tokens` |
| 融合去重失效 | 同一块在 top-5 出现两次 | 缓存指纹不含 schema 版本 |
| 精排抹平收益 | 改进被吃掉 | 精排用失效的信号打分 |
| 18% 语料不可检索 | 老式文件查不到 | 它们不用「第X条」编号 |
| 索引规模卡在 3 万 | 建 BM25 时崩溃 | SQLite 变量上限 |
| **反馈闭环从未落盘** | 界面显示"已反馈"，JSONL 恒为空 | `_submit` 里的 `msg = msg or {}` 遮蔽了闭包变量 |

**共同规律**：这些 bug 都不让程序报错，只让结果"看起来正常"。

所以这个项目里，**可观测性（覆盖率、元数据缺失率、拒答率、心跳、进度）
比指标本身更重要**。
