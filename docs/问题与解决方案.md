# 问题与解决方案

记录本项目从「造纸领域 demo」重构为「法规问答系统」过程中遇到的问题。

**这份文档的重点不是"改了什么"，而是"哪些错误是不报错的"** —— 下面绝大多数
问题都不会让程序崩溃，只会让结果安静地变差。这类问题靠跑一遍是发现不了的，
必须靠可观测性指标和对照实验。

## 一、知识库本体

### 1. 知识库与业务域完全错配

**现象**：系统被问「打浆度 °SR」「AKD 熟化」「靴式压榨 kN/m」，而回答来自
「用平底锅法和框架法造纸」「接着放到半条毛巾上」「用低温熨平毛巾」。

**根因**：全部语料 43 个 chunk：

```
sample_knowledge  14 条  ← 硬编码在脚本里的示例
expert_qa         15 条  ← LLM 生成的问答
PDF               14 条  ← 唯一文档：15 页 DIY 手工造纸小册子
```

那本 PDF 用 PyMuPDF 全文提取只有 **5,367 字符**（含版权页、目录）。它是科普
读物，讲如何在家里用搅拌机手工造纸；而系统面向的是工业造纸工艺。

**修法**：换域到中国法律法规，语料改为国家法律法规数据库。

**教训**：知识库的问题不是"不够大"，而是**根本不在同一个领域**。在换域之前
先问一句"库里有没有一条内容能支撑目标问题"。

---

### 2. 评测自证循环

**现象**：README 宣称「知识库内 Hit@5 = 100%」，任何改动都是 100%。

**根因**：评测集的 `relevant_chunk_indices` 指向一个硬编码 Python 列表的下标：

```json
{"id": "q001", "question": "打浆度一般控制在什么范围？", "relevant_chunk_indices": [0]}
```

真值是"seed 数据里的第 0 个 chunk"。这意味着出题时**只能看着 chunk 编问题**，
问题成了答案的改写。而"全量 84%"（42/50）与"知识库内 100%"（42/42）是同一
个数字的两种写法——8 条"知识库外"问题的真值为空，数学上必然 MISS。

**修法**：真值改为按 `(法规名, 条号)` 匹配 chunk 元数据，评测集因此可以脱离
语料编写；并**单独报告语料覆盖度**，把"语料没收录"和"检索没找到"分开。

**教训**：**评测集必须来自语料之外的独立来源。** 判据很简单——如果出题时你
看了语料，指标就不可信。

## 二、数据采集

### 3. 站点 WAF

**现象**：采集顺利跑约 150 次请求后被拦，之后全部失败。

**根因**：站点前置了网宿 WAF，两级反应：

1. 轻量：返回 302 + `wzws_cid` cookie，带着 cookie 重发即可通过
2. 量大：升级为 **JavaScript 挑战页**，需要执行 JS 才能拿到 cookie

关键是这个挑战是**冷却式**的——停手一段时间后确实会恢复。

**修法**：识别挑战后整体停下来等，而不是硬闯。等待时间随连续命中次数指数增长
（3 → 6 → 12 → 15 分钟封顶）。

**踩到的坑**：最初的检查逻辑只看"是不是 JSON"，而 JS 挑战页也是 `200 +
text/html`，于是被当成"数据格式错误"，把"被反爬拦住"误报成"接口变了"。

---

### 4. 熔断信号被 `except Exception` 吞掉

**现象**：一次运行积压了 **117 条"失败"**，但整轮并没有停止。

**根因**：熔断异常（`SiteThrottled`）继承自 `RuntimeError`，被单条失败的
`except Exception` 捕获，于是被当成"这一部法规失败了"，继续处理下一部——而
下一部立刻又触发熔断。结果是把后续每一部都标成失败，而不是干净退出。

**修法**：在每层显式 `except SiteThrottled: raise`。

**教训**：自定义的**控制流异常**必须与业务异常分开处理。用宽泛的
`except Exception` 包裹单条处理逻辑时，会顺手把控制信号也吞掉。

---

### 5. 任务停止只杀了包装进程

**现象**：`TaskStop` 之后日志停了，但文件数仍在增长。

**根因**：停止的是外层包装命令，真正的 python 采集子进程成了孤儿继续跑。
差点因此启动第二个采集器 —— **那会让请求速率翻倍，立刻触发 WAF**。

**修法**：按进程名 + 命令行匹配精确杀掉；并且在启动新采集前先检查心跳文件。

**教训**：长任务要有**外部可见的存活信号**（心跳），否则"看起来停了"和
"实际还在跑"无法区分。

---

### 6. 详情接口的 `content` 字段恒为空

**现象**：按文档拿到的"正文"字段始终是 `None`。

**根因**：实测 5 部法规全部为空。正文只能通过 docx 下载接口取得**签名 URL**
后再下载。

**修法**：流程改为 枚举 → 取签名下载地址 → 下载 docx → 解析。

**教训**：接口文档会骗人，**先探测真实响应再设计流程**。

---

### 7. 扫描件与老式 `.doc`

**现象**：部分法规解析失败，报 `BadZipFile` 或
`KeyError: There is no item named 'word/document.xml'`。

**根因**：两种不同的情况被同一个错误掩盖：

- **扫描件 PDF**：4.1MB 但文字层 **0 行**，需要 OCR 才能处理
- **老式 `.doc`**：文件头是 OLE2 魔数 `\xd0\xcf\x11\xe0`，被当作 zip 打开后
  找不到 `word/document.xml`

**修法**：
- 加 OLE2 魔数识别，直接报"旧版 .doc 格式"
- PDF 无文字层时记为**失败**，而不是 `no_articles` —— 后者会让人以为
  "文档本来就没条文"
- 两条兜底路径都失败时，**把两边的原因都写进报告**

**教训**：错误信息必须能区分不同的失败原因，否则会把人引向错误的方向。

## 三、解析与索引

### 8. 条首必须行首锚定

**现象**：海商法解析出 382 个"条文"，实际只有 310 条。

**根因**：正则 `第[一二三…]+条` 没有锚定行首，于是正文里的**引用**也被当成条首：

```
第一条　……依照本法第三百零二条规定处理。
                ↑ 被误判为条首
```

**修法**：`(?m)^\s*第[一二三…]+条`。

**教训**：这条设计后来还救了"兜底切分"——那 365 部老式文件里出现的「第X条」
**全部是对其他法规的引用**（如「将《安排》第一条修改为…」）。正因为锚定严格，
它们才没被误当成本文的条文。

---

### 9. 「第十七条之一」解析成 11

**现象**：刑法条号看起来断裂（17 → 11 → 18），505 条里 35 个号重复。

**根因**：`cn_to_int("第十七条之一")` 把结尾的「一」也算进去了：
十(10) + 七(7)… 然后「之一」的「一」→ 结果 11。

**修法**：先按 `第(?P<num>…)条(?:之(?P<sub>…))?` 拆开，再分别转数字。

**教训**：**这个 bug 我犯了两次** —— 在 `law_parser.py` 修完之后，又在
`evaluator.py` 里因为重复实现而重现。所以最后抽成了
`src/utils/cn_numeral.py` **共享模块**。数值解析逻辑绝不要写两遍。

---

### 10. 源库有重复条目

**现象**：索引里出现重复块互相竞争排名。

**根因**：源库中同一部法、同一效力状态、条文完全相同，但 `bbbs` 不同：

```
中华人民共和国公司法    sxx=2    2 份   bbbs 分别以 2c909fdd / ff808081 开头
中华人民共和国村民委员会组织法  sxx=2  2 份
中华人民共和国城市居民委员会组织法 sxx=2  2 份
```

索引以 `bbbs` 为 source，两份都会入库。

**修法**：按 `(标题, 效力状态)` 去重，保留条文更多的那份。

---

### 11. `None` 元数据导致索引崩溃

**现象**：嵌入跑了 32 分钟成功后，下一步建 BM25 时崩：

```
TypeError: argument 'metadatas': Cannot convert Python object to MetadataValue
```

**根因**：Chroma 只接受 `str/int/float/bool`。实测 **117 部法规的施行日期在源
接口里是 `null`**，而 `dict.get("sxrq", "")` 在"键存在但值为 None"时返回的是
`None` 而不是默认值。

**修法**：加 `sanitize_meta()` 在切分侧统一清洗（磁盘上已有的 JSON 也带 None，
所以必须在切分侧拦，不能只改采集器）。

**教训**：`dict.get(k, default)` 对 **JSON null 不生效**。这是个容易反复踩的坑。

---

### 12. SQLite 变量上限把索引规模卡在 3 万条

**现象**：

```
chromadb.errors.InternalError: error returned from database:
    (code: 1) too many SQL variables
```

**根因**：`collection.get()` 不带 limit 时试图一次取回全部记录，Chroma 的
SQLite 后端因此撞上 `SQLITE_MAX_VARIABLE_NUMBER`（约 32,766）。
**实测 27,672 条可以通过，54,618 条失败。**

**修法**：加分页取数 `fetch_all(collection, batch=5000)`，并把所有调用点换过来。

**教训**：这个 bug **只在规模上去之后才出现**。小数据上跑通不代表可扩展。

---

### 13. 18% 的语料完全检索不到

**现象**：365 部法规（占语料 18%）解析出 0 条。

**根因**：它们**本来就不用「第X条」编号**。抽样看原文：

```
《保护海底电缆规定》(1973)
  (一) 保护海底电缆是加强海防建设的重要措施……
  (二) 舰艇、商船、外轮等舰船锚泊，要避开敷设有海底电缆的禁区……
  → 「第X条」出现 0 次
```

是 1950–70 年代的老式规范性文件，以及修改/补充决定（用「一、」）。

**修法**：三级兜底切分（只在找不到「第X条」时启用）：

| 级别 | 依据 | 用于 |
|---|---|---|
| 1 | `一、` 行首 | 修改/补充决定、早期文件 |
| 2 | `（一）` 行首 | 更早期的文件 |
| 3 | 段落分组 | 批复/复函（无编号散文） |

两个防误判设计：**要求 ≥2 个标记**才认作结构（避免散文里偶然一个「一、」
凭空造出层级）；级别 3 跳过版头（判定用"段落过短 **或** 含版头提示词"）。

**效果**：无条文文件从 365 → **0**，多出 1,473 个可检索块。

## 四、检索与排序

### 14. 陈旧缓存被判定为"新鲜"，元数据全丢

**现象**：同一块在 top-5 里出现两次，其中一次 `META: None`；引用来源全部
退化成「知识库」。

**根因**：`_doc_signature` 只哈希**文档文本**，不包含序列化状态的 schema 版本。
代码后来给缓存加了 `_doc_ids` / `_doc_metas` 字段，但旧缓存因为"文本没变"
仍被判为新鲜而被加载 → `_doc_ids` 退化成 `chunk_{i}`，与向量库的真实 id
`{source}_chunk_{i}` 永不相等 → 融合阶段的去重前提失效。

**修法**：指纹里加入 `_SCHEMA_VERSION`；`load()` 遇到不匹配的版本直接返回
`False` 让调用方重建。

**教训**：缓存的失效判断必须覆盖**所有**影响正确性的状态，不只是"输入数据"。

---

### 15. 重复 sigmoid 让拒答完全失效

**现象**：问「明天天气怎么样」，系统返回《国旗法》第十三条并标注了出处。

**根因**：`CrossEncoder.predict()` **默认已经应用了 Sigmoid**，返回的就是概率。
代码里又套了一层：

```python
prob = 1.0 / (1.0 + math.exp(-logit))     # ← logit 其实已经是概率
```

sigmoid 是单调的，**排序不受影响** —— 正因如此极难发现 —— 但所有分数被压缩
进 `[0.5, 1.0]`。于是任何低于 0.5 的阈值都形同虚设，**拒答分支成了死代码，
而检索看起来一切正常**。

**证实方式**：域外问题的得分**恰好是 0.500**（= sigmoid(0.0)），这个过于整齐
的数字暴露了问题。

**修法**：去掉重复的 sigmoid。

**补充**：这个 bug 是我在修「加权乘在 logit 上」时**自己引入的**，而当时随手
定的 0.35 阈值恰好把它掩盖了。

---

### 16. 权威加权乘在负 logit 上，方向反了

**现象**：本该被加权的文档反而被降权。

**根因**：`score * 1.3` 直接作用在 cross-encoder 的**原始 logit** 上。而
bge-reranker 对无关 pair 输出负数：`-3.0 × 1.3 = -3.9`，**越乘越负**。

**修法**：在 sigmoid 之后的概率域加权。

---

### 17. 关键词自指命中

**现象**：语料里最不可信的内容被系统性置顶。

**根因**：权威加权词表含「**专家**」，而语料里的问答块格式是
`【专家经验问答 #N】` —— **完美自指命中，全体 ×1.3**。

**修法**：去掉这类词。**权威关键词必须指向外部标识，不能是语料自己给自己贴的标签。**

---

### 18. 精排被彻底移除（两次实测 + 排除技术性原因）

**现象**：

```
无改写 + 无精排   Hit@5 = 0.133
有改写 + 无精排   Hit@5 = 0.567   ← 最优
有改写 + 精排     Hit@5 = 0.233   ← 精排把收益吃掉了
```

**第一轮归因（只对了一半）**：交叉编码器用 `(用户原问题, 条文)` 打分 ——
**而"用户原问题"正是那个因语域差而失效的信号**。于是推论是"让它用**改写后**的
文本打分就对了"。

**第二轮实测推翻了这个推论。** 把 HyDE 包在精排**外层**（改写文本同时用于召回
与打分），同一批 25 条题：

| 配置 | Hit@5 |
|---|---|
| 改写 + **无精排** | **0.520** |
| 改写 + 精排（改写文本打分） | **0.280** |

n=25 时标准误约 10 个点，−24 点是 2.4 个标准误 —— **换用正确信号之后精排依然
是负作用**。

**再排除技术性原因。** 怀疑输入超过 CrossEncoder 长度上限被截断，查配置与库源码：

```
config.json             max_position_embeddings = 8194
tokenizer_config.json   model_max_length = 8192
CrossEncoder(max_length=None)   # 不覆盖，沿用 tokenizer 值，被模型能力封顶
→ 实际有效长度 8192；我们的输入约 500–600 token，无截断
```

**结论：精排在这条任务上就是不行。** 两种信号都测过，长度因素已排除，口径收窄到
"模型与任务的匹配问题"，而不是链路里的某个 bug。生产配置**永久关闭精排**。

**教训**：这是**从下游开始调参**的典型代价。当时在调精排阈值，而瓶颈在召回 ——
精排只能"从候选池里挑"，池子里没有正确答案时它无能为力。正确顺序是从上游往下：
先用 `scripts/diagnose_recall.py` 定位瓶颈在哪一段，再决定改什么。

---

### 19. 融合方式不是瓶颈

**现象**：把组内 min-max 归一化换成 RRF（Cormack SIGIR 2009，只用名次），
召回率**没有变化**。

```
@20    0.547 → 0.554
@50    0.696 → 0.676
@100   0.736 → 0.723
```

（148 条样本标准误约 4.1 点，全在噪声内。）

**修法**：保留 RRF（不需要分数校准、代码更短），但**不把它当作性能改进**。

**教训**：一次"看起来合理"的改造没有效果，也是有价值的结果——它排除了一个
嫌疑方向，把注意力推向真正的瓶颈（召回）。

---

### 20. 查询改写的收益（最终解法）

**现象**：语义召回 @20 只有 0.480，但 @500 有 0.858 —— **全局可分，局部不精**。

**根因**：**语域差**。用户写「公司拖欠我三个月工资我能主张什么」（口语），
条文写「用人单位应当按照劳动合同约定和国家规定，向劳动者及时足额支付劳动
报酬」（书面）。

**修法**：HyDE —— 先用 LLM 生成一段"如果法律要回答这个问题，条文大概会怎么
写"的文字，把它**拼在原始问题后面**一起嵌入（保留原问题的原因是它承载了
事实描述，生成的法条里没有）。

**实测**（148 条，同一批题）：

| 查询表示 | @20 | @50 | @100 |
|---|---|---|---|
| 原始问题 | 0.480 | 0.649 | 0.723 |
| 仅假设性条文 | 0.736 | 0.858 | 0.899 |
| **问题 + 假设性条文** | **0.757** | 0.872 | 0.905 |
| 两路取并集 | 0.777 | 0.878 | 0.912 |

**教训**：方向判断错过一次——我曾怀疑是嵌入模型容量不够（要换 bge-m3），
实测证明**模型没问题，是喂给它的查询不对**。

## 五、生成：推理模型的坑

### 21. 配置的模型名在服务端不存在

**现象**：问答返回空字符串。

**根因**：`.env` 没设 `DEEPSEEK_MODEL`，代码默认 `deepseek-v4-flash`。但端点
实际只提供：

```
deepseek-flash
deepseek-v4-pro
```

**修法**：改用实际存在的模型名，并在 `.env.example` 里写明。

---

### 22. 推理吃光 token 预算，正文为空

**现象**：真实法律问题，按原有配置（`max_tokens=1024`）返回**零字**：

```
max_tokens= 512   推理  846字   正文 0字   finish=length
max_tokens=1024   推理 1698字   正文 0字   finish=length
max_tokens=2048   推理 3546字   正文 0字   finish=length
max_tokens=4096   推理 6914字   正文 0字   finish=length
```

**根因**：两个模型都是**推理模型**，会先产出不可见的 `reasoning_content`。
原有的 512/1024/2048 预算是给**非推理模型**设计的。预算被推理耗光时，
`content` 为空而 `finish_reason="length"` —— **看起来像"模型没回答"**。

**修法（第一版）**：调大 `max_tokens` + 失败重试。

**修法（最终版，见下）**：用 `reasoning_effort` 直接控制推理量。

**为什么一直没被发现**：整个开发过程中**从没跑过一次完整的 LLM 问答** ——
采集、解析、索引、召回、评测都不经过 LLM。而且它的表现是"模型没回答"，
很容易被误判成模型能力问题或提示词问题。

---

### 23. 过度推理：又慢又短

**现象**：同一个问题，三种推理档位：

| 设置 | 耗时 | 推理 | 正文 |
|---|---|---|---|
| baseline | **78.9s** | 9402字 | 1058字 |
| `reasoning_effort="low"` | **9.4s** | 192字 | **1223字** |
| `reasoning_effort="none"` | 6.2s | 0字 | 936字 |

**根因**：不设限时模型**过度推理** —— 把预算耗在分析上，正文反而更短。
`effort=low` 不但快 8.4 倍，答案还更完整。

**修法**：

- **查询改写**：`reasoning_effort="none"` —— 它是**机械转换**任务（把口语
  搬进法条语域），不需要法律分析。实测从 25 秒降到 **3.5 秒**，且空结果从
  6–9% 降到 **0**
- **答案生成**：`reasoning_effort="low"` —— 需要法律推理，但不能不设限

**连带效果**：空答案问题**从结构上消失**了（推理不再吃光预算），不再需要靠
调大 `max_tokens` 打补丁。

**教训**：推理量是需要**显式控制**的工程参数，不是"越多越好"。

---

### 24. 提示词影响推理量

**现象**：HyDE 改写用「你是一位立法工作者，请写出一段…」时，推理长达
3000–5000 字，**50% 的调用返回空**。

**修法**：改成直白的机械指令「用中文法条的措辞和句式，把下面的问题改写成
一段法条正文」——产出质量一样，推理量明显下降，空结果率降到 6%。

**教训**：身份设定和开放式的任务描述会诱发大量推理。**对机械任务要用机械的
指令。**

---

## 六、评测方法本身的坑

### 25. 分层采样让样本比全集难得多

**现象**：

```
全量（6,926 条）hybrid-only     Hit@5 = 0.319
按法名分层采样（72 条）         Hit@5 = 0.125
```

差距太大，不是采样误差。

**根因**：按**法名**分层，各法规在评测集里的条数相差两个数量级
（民法典 1,935 条 vs 公司法 51 条），从每部法各取等量把小法超采样了几十倍。

**修法**：改为**均匀随机采样**（带固定种子保证可复现）。

**教训**：分层采样只有在**层内同质、层间差异大**时才合理。这里恰恰相反。

---

### 26. 指标自己算错了

**现象**：报告显示「召回结果元数据缺失率 **81.1%**」，但实际元数据是完整的。

**根因**：分母写成了 `样本数 × max_k`。但相关性下限会过滤候选，很多查询只
返回 0–2 条 —— **返回 0 条时那 10 个"缺失"槽位根本不存在**。等于把"拒答生效"
算成了"元数据丢失"。

**修法**：分母改为实际召回条数。

**教训**：**先验证量具，再读数。** 我这次多次先报出数字、后才发现指标本身有
问题，顺序完全反了。

---

### 27. 采样数量与请求不符

**现象**：`--sample 120` 实际返回 92 条。

**根因**：`per = n // 层数` 的整除取整 + 空层。

**修法**：均匀采样，恰好 N 条。

---

## 七、工程与可观测性

### 28. 无法区分"冷却中"和"已死"

**现象**：采集器会静默数十分钟（WAF 冷却），从外部看和进程挂掉没有区别。

**修法**：写心跳文件 `data/meta/crawl_heartbeat.json`，记录状态
（`starting/fetching/cooling/done`）、累计计数、当前处理的法规。状态脚本据此
准确显示。

---

### 29. 长时间操作没有进度输出

**现象**：索引嵌入 5 万条、评测 600 条、HyDE 生成 150 次，全程无输出。

**修法**：三处都补上进度行（已处理 N/总数、速率、预计剩余）。
Chroma 的 `add` 和评测循环本身不打进度，必须自己加。

---

### 30. 状态脚本显示上一次运行的数据

**现象**：刚启动的一轮采集，监控显示「失败 **1976** 部」——那是上一轮的累积。

**根因**：报告只在每个类别结束时落盘，新的一轮在跑到第一个类别结束前，
监控读到的是旧文件。

**修法**：采集启动时立刻用空报告覆盖；状态脚本对陈旧报告标注并忽略。

---

### 31. 启动时崩溃：`UnboundLocalError`

**现象**：新加的一行 `_flush(catalog, report)` 插到了 `catalog` 变量定义**之前**，
采集一启动就崩。

**教训**：这类错误靠肉眼 review 容易漏，**启动后立刻看一眼日志**是最便宜的
验证。

---

## 八、架构层面的取舍（尚未解决）

### 32. 查询改写与拒答机制相互冲突

**现象**：HyDE 让域外问题也能匹配到真实条文：

```
Q: 明天天气怎么样
→ HyDE 把它改写成「……明日天气信息由县级以上气象主管机构统一向社会发布」
→ 匹配到了真实的《中华人民共和国气象法》第二十二条
```

**根因**：**HyDE 的作用就是把任何问题都洗成法条腔，这恰好摧毁了"语料能不能
答这个问题"的判别信号。**

**实测：余弦阈值区分不开**

```
库内问题  n=141   0.822 – 0.984（中位 0.903）
域外问题  n= 12   0.770 – 0.915（中位 0.822）
                        ↑ 域外最大值高于库内最小值
```

阈值定在 0.75 时误拒 0%，但域外问题 **100% 漏放**。

**其他被排除的方案**：

- **精排做门控**：交叉编码器的分数分布同样重叠（正确条文中位 0.433 / 无关
  条文 p90 0.585），且要付 10 秒延迟
- **只用相似度不用阈值**：没有绝对尺度可比

**当前状态**：靠**提示词层**约束。模型会诚实说明"知识库不含实时天气数据"，
但仍会附上相关法条。实测输出：

> 我无法提供具体的明日天气预报。我的知识库收录的是法律法规条文，不包含实时
> 或未来的气象数据。根据《中华人民共和国气象法》第二十二条……如需了解明日
> 天气，建议通过中国气象局或当地气象台站的官方渠道查询。

**这是权衡，不是纯 bug** —— 要不要为拒答能力牺牲 28 个点的召回，需要按实际
使用场景决定。

## 九、环境

### 33. HuggingFace 缓存的过期否定标记

**现象**：模型加载卡 20 多分钟，最后报
`Unrecognized processing class in BAAI/bge-reranker-v2-m3`。

**根因**：缓存里有 `.no_exist/` **否定缓存标记**，记录着"某个文件不存在"。
即使文件其实已经在缓存里，`transformers` 也会跳过本地去请求网络，超时后重试。

**修法**：

```bash
find ~/.cache/huggingface/hub -maxdepth 2 -name ".no_exist" -type d -exec rm -rf {} +
```

清除后模型可**完全离线**加载（实测 embedding 0.3s、reranker 3.0s）。

---

### 34. 长时间阻塞难以定位

**现象**：一个进程静默 56 分钟，输出文件不再增长，但进程活着。

**定位方法**：看**进程 CPU 时间**是否增长：

```
第一次: CPU 5540.5s
25 秒后: CPU 5540.5s   ← 完全没动，说明阻塞在 I/O 而非计算
```

**根因**：OpenAI SDK **默认自带重试与退避**，与自定义的 `timeout` 叠乘，
单次调用可能等十几分钟。

**修法**：`max_retries=0` + 缩短 timeout；再加一层**累计预算闸**（超过总预算
后整层自行关闭、余下直接透传），保证失败不会拖垮整轮。

## 十、检索链路的取舍（实测驱动）

这两条都是链路参数上的取舍，共同点是**先量再定** —— 一条量完决定不改，
一条量完改了（`top_k` 5 → 12）。

### 35. Agent 路径的改写开销（已实测，非猜测）

**现象**：工具调用会触发查询改写，`max_iterations=10` 时最坏累计 37 秒。

**实测澄清了一件事**：我最初判断"工具传的是关键词串，改写价值有限"——**这是错的**。

```
输入: 民间借贷 常见误区 法律风险 责任 举证 时效 注意事项
改出: …主张借贷关系成立的一方应当对借贷合意及款项交付承担举证责任。
      约定不明的，视为不支付利息。利率超过一年期 LPR 四倍的部分不予支持。
      诉讼时效期间为三年…                    ← 举证、利率上限、时效全命中
```

对含法名的查询改写还**提升精度**：

```
「劳动合同法 第三十条」  原文 top2 → 改写后 top1
「第五百八十五条」       原文 top1 是别的法，改写后 top1 是正确的民法典条文
```

至于 `"第三十条"`（光有条号无法名）——**原文同样找不到**（返回的是另一部法的
第 30 条），所以不是改写造成的退化，是查询本身有歧义。

**提出优化，并用测量否决了它**：

自然的想法是"只改写用户原问题，工具查询跳过改写"，省下那 37 秒。实测
（`scripts/measure_agent_queries.py`，60 条题）：

| 查询形态 | @20 改写前→后 | 增益 |
|---|---|---|
| 完整问题 | 0.47 → 0.80 | **+0.333** |
| 关键词式（法条清单） | 0.42 → 0.50 | +0.083 |
| 关键词式（风险误区） | 0.35 → 0.50 | +0.150 |

工具式查询的增益小得多（语域差在自然语言问题上最大，关键词串本就没多少"口语"
可搬），**但仍然是正的**。跳过改写的代价是 8–15 个点的召回，换 37 秒的**最坏
情况**——不划算。而且缓存已让重复的工具查询零成本，真实开销远低于最坏值。

**结论：不改。**

**这是本项目中第一次"先测再改"完整走完，结果是方案被否决。** 值得与前面几次
对照： "精排更差""余弦能区分拒答""改写对工具查询价值有限" 这三条都是**先下
结论、后验证**，三次都翻了。方案被自己的数据否掉，正是测量在起作用 —— 这与
〈方法论教训〉里"先下结论、后验证，必然翻车"那条讲的是同一件事。

---

### 36. top_k 取多少：一条诚实的曲线

**现象**：`top_k` 原为 5。实测它是"决定性条文够不够得着"的直接原因：

问「公司没交社保，离职能否要赔偿」，法条链是 劳动合同法 **38 条**（可解除）→
**46 条**（应付经济补偿）→ **47 条**（计算标准），而 38/46 在真实链路里排
第 **11、12** 名，前 10 名全是匹配了问题表面字眼（"社保""赔偿"）但法律上不
决定结论的条文。取 5 条时模型只能诚实地说"资料未覆盖"，取 12 条即可完整作答。

**召回率 vs k**（150 条评测题，HyDE + 混合检索）：

| k | 1 | 3 | 5 | 8 | **12** | 16 | 20 | 30 |
|---|---|---|---|---|---|---|---|---|
| Hit Rate | 0.360 | 0.453 | 0.540 | 0.613 | **0.667** | 0.687 | 0.707 | 0.800 |
| **MRR** | 0.360 | 0.401 | 0.422 | 0.433 | **0.438** | 0.439 | 0.440 | 0.445 |
| Precision | 0.360 | 0.151 | 0.109 | 0.078 | 0.057 | 0.044 | 0.037 | 0.028 |

**怎么读**：Hit Rate 从 5→30 涨了 26 个点，但 **MRR 从 k=8 起就平在 0.44 不动**。

也就是说 —— **涨的不是排序质量，是"捞得更多"**。正确条文没有被排到前面，只是
随着 k 增大被网了进来。同时 Precision 从 0.109 掉到 0.028：k=30 时喂给模型的
30 条里平均只有 0.84 条相关，其余是噪声。

**取 k=12 的依据**：k=5→12 是单位收益最高的一段（每条 +1.35 点），12→20 掉到
+0.5。20→30 那段虽然 +9.3，但 150 条样本标准误约 4 点，**可能是噪声，不足为凭**。

**诚实的话**：**加大 k 是在绕开排序问题，不是在解决它。** 排序问题的正解（精排）
已实测排除（见第 18 条），当前只能这样缓解。权衡写进了 `rag_pipeline.py` 的
`top_k` 注释。

## 十一、Web 界面与用户反馈

### 37. 反馈闭环从未落盘（异常发生在写盘之前）

**现象**：Web 端点 👍/👎 报错。但更值得记录的是**它此前一直"看起来正常"** ——
界面照常显示「已反馈：有帮助」，而 `data/feedback.jsonl` 始终是空的。

**根因**：嵌套函数里的变量遮蔽。

```python
def render_feedback(msg_index, msg=None):
    def _submit(rating):
        st.session_state.feedback[str(msg_index)] = rating   # ← 先执行，成功了
        msg = msg or {}                                      # ← 这里炸
        feedback.record(rating, question=msg.get("question", ""), ...)
```

`_submit` 里的这个赋值让 `msg` 变成了**它自己的局部变量**，右侧的 `msg` 于是读到
尚未赋值的局部名，点击即抛：

```
UnboundLocalError: local variable 'msg' referenced before assignment
```

作者的意图是兜住 `msg=None` 的默认值，结果把闭包变量遮住了。

**为什么症状具有欺骗性**：写入 `session_state` 那行在异常**之前**，所以按钮的
"已反馈"状态照常更新。用户看到的是"反馈了，但页面弹了个错"；从磁盘看则是
**一条记录都没有** —— 这个闭环从未真正工作过。

**为什么测试没抓到**：`tests/test_ui_components.py` 用假 streamlit 做渲染冒烟，
而 `_FakeSt.button()` **恒返回 `False`** —— 整条点击路径从未被执行过。冒烟测试
覆盖了"渲染不抛异常"，点击那条分支是空的。

**修法**：局部名改为 `_msg`；并让假 streamlit 支持模拟点击（`click_key`），
补 4 个用例走真实的点击路径（其中 3 个在旧代码上会失败）。

**教训**：

1. **遮蔽（shadowing）不报错。** `x = x or default` 在嵌套函数里是一条**改变
   作用域**的语句，不是"读一下 x"。闭包里要兜默认值，必须换名。
2. **副作用在异常之前，会把失败伪装成成功。** 凡是"先更新 UI 状态、再落盘"
   的顺序，都要问一句：中间抛异常了，用户看到的是什么？
3. **测试替身恒返回 `False`，等于把那条分支删掉了。** 代码"被执行过"，
   覆盖率数字看不出来 —— 但按钮永远不会被按下。

## 十二、方法论教训

把上面这些问题抽象一下，反复出现的是这几条：

**1. 先验证量具，再读数。**
多次先报出指标、后发现问题出在指标本身（采样偏差、分母算错）。正确顺序是
**先证明这个测量能反映它声称反映的东西**。

**2. 从上游往下测，不要从下游调参。**
我在调精排阈值和融合方式，而瓶颈在召回（第 18、19 条）。精排只能"从候选池里
挑"，**池子里没有正确答案时，挑得再准也没用**。`diagnose_recall.py` 之所以存在，
就是为了先定位瓶颈在哪一段。

**3. "不报错但结果不对"的 bug 最危险。**
本项目中这类占绝大多数：重复 sigmoid（第 15 条）让排序看起来正常、陈旧缓存
（第 14 条）让引用退化成"知识库"、过度推理（第 23 条）只是让答案变短。它们都
需要**可观测性指标**才能暴露：覆盖率、元数据缺失率、拒答率、心跳、进度。

**4. 一次"没有效果"的实验同样有价值。**
RRF 融合测出无变化（第 19 条）、精排两次实测均更差（第 18 条）—— 这些负结果
排除了嫌疑方向，把注意力推向真正的瓶颈。

**5. 先下结论、后验证，必然翻车。**
本会话中"精排更差""余弦能区分拒答""改写对工具查询价值有限""换个信号精排就能
工作"这四条判断，**全部被后续测量推翻**。写进文档前必须先跑数据 —— 其中
"改写对工具查询价值有限"那条甚至已经被我写进三份文档，事后才发现是错的。

**6. 数值解析、正则匹配这类逻辑绝不要写两遍。**
条号解析的 bug（第 9 条）因为重复实现而犯了两次，最后只能靠抽共享模块解决。

**7. 文档的批量编辑要小心。**
用 `s[索引:]` 做替换时切到文件末尾，会**静默删掉后面的整节**。本文件的方法论
一节就因此丢过一次。另外**不要在文档里写死行号** —— 这类引用自己会腐烂，
改一次别处它就指错了。
