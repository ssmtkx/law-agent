# 评测结果

本文件记录项目实际跑出来的数字，以及**这些数字能说明什么、不能说明什么**。

> 复现命令见各节末尾。原始数据：`data/eval_law.json`（评测集）、
> `data/agent_eval_results.json`（Agent 逐条结果）。

## 一、评测集从哪来

**这是全部指标可信度的前提。**

法律领域的评测集**不能**照着语料自己写——用检索到的条文反推问题，得到的是循环
论证。本项目此前正是如此：真值是"硬编码列表的下标"，问题成了答案的改写，于是
README 上的「知识库内 Hit@5 = 100%」实为 42/42，与 84%（42/50）是同一个数字的
两种写法，不携带任何信息。

现在使用**独立于采集语料**的来源：

| 用途 | 来源 | 规模 |
|---|---|---|
| 主评测 | [EQUALS](https://github.com/andongBlue/EQUALS)：问题来自真实法律问答社区，答案由法学标注者从条文中抽取 | 6,914 条 (问题, 法条, 答案) |
| 拒答 | 自建域外问题集（GDPR、美国专利法、自动驾驶责任、AI 生成物著作权…） | 12 条 |

真值按 **(法规名, 条号)** 匹配 chunk 元数据，因此评测集可以脱离语料编写。

**语料覆盖度**（全量 6,926 条评测集）：

```
黄金条文覆盖率: 91.7%
可答条目: 6337/6914
```

覆盖率是所有指标的分母前提——语料没有的条文必然 MISS，把"语料缺失"和
"检索失败"混在一起算的 Hit Rate 不是检索能力的度量。

## 二、RAG 检索评测

### 2.1 配置对比（30 条评测题，同一批题）

| 配置 | Hit@5 |
|---|---|
| 无查询改写 + 无精排 | 0.133 |
| 无查询改写 + 精排 | 0.233 |
| **有查询改写 + 无精排** | **0.567** ← 生产配置 |
| 有查询改写 + 精排（改写文本打分） | 0.280 |

两个结论：

1. **查询改写是主要收益来源**（0.133 → 0.567）
2. **精排是净负作用**，两次实测均如此：用原问题打分时 0.567 → 0.233；改用改写
   文本打分后仍是 0.520 → 0.280（同批 25 条）。并已排除截断（有效长度 8192，
   输入约 500–600 token）

### 2.2 召回率 vs top_k（150 条评测题）

| k | 1 | 3 | 5 | 8 | **12** | 16 | 20 | 30 |
|---|---|---|---|---|---|---|---|---|
| Hit Rate | 0.360 | 0.453 | 0.540 | 0.613 | **0.667** | 0.687 | 0.707 | 0.800 |
| MRR | 0.360 | 0.401 | 0.422 | 0.433 | **0.438** | 0.439 | 0.440 | 0.445 |
| Precision | 0.360 | 0.151 | 0.109 | 0.078 | 0.057 | 0.044 | 0.037 | 0.028 |

**Hit Rate 从 5→30 涨 26 个点，但 MRR 从 k=8 起平在 0.44。**

含义：**涨的不是排序质量，是"捞得更多"**。正确条文没被排到前面，只是随着 k 增大
被网了进来。同时 Precision 从 0.109 掉到 0.028——k=30 时喂给模型的 30 条里平均
只有 0.84 条相关。

`top_k=12` 的取法：5→12 是单位收益最高的一段（每条 +1.35 点），12→20 掉到 +0.5。
20→30 那段虽然 +9.3，但 150 条样本标准误约 4 点，**可能是噪声，不足为凭**。

> **诚实的话：加大 k 是在绕开排序问题，不是在解决它。** 排序问题的正解（精排）
> 已两次实测排除，当前只能这样缓解。

### 2.3 查询改写实验（148 条，同一批题）

| 查询表示 | @20 | @50 | @100 |
|---|---|---|---|
| 原始问题 | 0.480 | 0.649 | 0.723 |
| 仅假设性条文 | 0.736 | 0.858 | 0.899 |
| **问题 + 假设性条文**（生产用法） | **0.757** | 0.872 | 0.905 |
| 两路取并集 | 0.777 | 0.878 | 0.912 |

选"问题+条文拼接"而非"两路取并集"：后者只高 2 个点（在噪声内），却要多一路检索
和按 id 合并的逻辑。

### 2.4 候选池诊断（148 条）

定位瓶颈用的。它把"找不到"（召回问题）与"排不上"（排序问题）分开：

| 召回方式 | @20 | @50 | @100 | @500 |
|---|---|---|---|---|
| BM25 | 0.284 | 0.392 | 0.446 | 0.574 |
| 语义 | 0.480 | 0.642 | 0.723 | 0.858 |
| 融合 | 0.547 | 0.696 | 0.736 | 0.858 |

**语义 @500 有 0.858 而 @20 只有 0.480** —— 正确条文 86% 的时候确实在库里能被
召回，只是排不进前 20。这个数字把方向从"换嵌入模型"扭向了"改查询"。

顺带排除一个假设：嵌入截断只影响 **0.8%** 的条文（token 中位 130，p90 270）。

## 四、延迟与吞吐

| 环节 | 耗时 | 说明 |
|---|---|---|
| 查询改写 | ~3.5 秒 | `reasoning_effort="none"`（改写是机械转换，不需要推理） |
| 检索 | ~1 秒 | 混合检索，无精排 |
| 答案生成 | 9–14 秒 | `reasoning_effort="low"` |
| **端到端** | **9–17 秒** | |

推理量的控制是主要收益：

| 设置 | 耗时 | 推理 | 正文 |
|---|---|---|---|
| 不设限 | 78.9s | 9402字 | 1058字 |
| `reasoning_effort="low"` | **9.4s** | 192字 | **1223字** |

不设限时模型**过度推理**——把预算耗在分析上，正文反而更短，而且这正是**空答案的
根因**（推理吃光 `max_tokens`）。

索引侧：嵌入 37 条/秒（CPU，bge-small-zh），57,066 条约 34 分钟。

## 五、这些数字不能说明什么

**这一节比上面的数字更重要。**

### 5.1 样本量限制了精度

| 实验 | 样本 | 标准误 | 能说明 | 不能说明 |
|---|---|---|---|---|
| 召回 vs k | 150 条 | ~4 点 | 趋势（5→30 涨 26 点） | 相邻 k 的小差异 |
| 配置对比 | 30 条 | ~9 点 | 改写带来的大跨度提升 | 0.567 与 0.520 这类小差 |
| 精排两轮 | 25–30 条 | ~9–10 点 | 精排的 −24 点下降 | 精确的降幅数值 |
| Agent | 20 条 | — | 链路可用、四维评分正常 | 精确的分数 |

### 5.2 Agent 评测的 95.2 有两处已知偏差

1. **a020 的标签是错的**。它被标为"知识库覆盖不到"，但语料后来补全了
   （《关税法》《增值税法》都采到了），agent 检索到真条文并正确作答——**它答对了，
   却被我的标签当成拒答失败**。已在本文件写作时更换为真正的域外问题，但尚未重新测量。

2. **引用评分曾不认具名格式**。评分器只匹配 `[来源N]`，而 a020 写的是
   `[来源：关税法第五条]`——**信息量更大**，却被判为"没有引用"。已修复并补测试。

### 5.3 Tool Selection 量的是人工预设，不是正确性

4 条扣分项（a002/a004/a009/a015）都是"预期调 2 个工具、实际调了 1 个"，而那 4 条
在**结构、引用、关键词三项都是满分**。我们的语料全是法条，"常见误区"那类工具本质
只是换关键词再检索一次，调不调都能出好答案。

**这个维度偏低不代表工具选错了**，要结合另外三维一起看。

### 5.4 检索指标 ≠ 答案质量

上表的 Hit Rate / MRR 全部是**检索层**指标。项目**没有端到端的答案正确性评测**——
即"给一段回答，判断法律结论对不对"。Agent 的四维评分里也只有关键词覆盖能间接反映
内容，仍然不是法律正确性判断。

### 5.5 拒答能力未单独测量

当前检索层没有相关性下限（HyDE 与"语料能不能答"的判别信号天然冲突，余弦与精排
两种方案均实测排除），拒答只靠提示词层约束。**因此没有拒答率数字**——评测报告里
那一栏会显示 0%，那是"没有机制"而非"机制失效"。

## 六、复现命令

```bash
# 评测集（需先下载 EQUALS 到 data/external/equals/）
python scripts/build_eval_set.py                    # 转换 + 核对覆盖度

# 检索评测
python eval_rag.py --dataset data/eval_law.json --hyde --sample 150 --k 1,3,5,8,12,16,20,30

# 召回诊断（定位瓶颈在哪一段）
python scripts/diagnose_recall.py --sample 150 --depth 20,50,100,500

# 查询改写对比实验
python scripts/test_hyde.py --sample 150

# Agent 评测（需要 API Key，20 条约 25 分钟）
python eval_agent.py --save data/agent_eval_results.json

# 用户反馈
python scripts/feedback_stats.py --bad 10
```
